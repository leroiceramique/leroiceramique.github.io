دليل البيئة التجريبية (Staging) — مخزون السيراميك Le Roi Céramique
══════════════════════════════════════════════════════════════════════════════════════

فلسفة الحل (بأقل تغيير ممكن، كما طلبت):
  نفس المشروع، نفس الكود، نفس حسابك — بلا أي مشروع جديد من الصفر.
  • فرع واحد إضافي على GitHub اسمه staging (الرسمي main يبقى كما هو تماماً).
  • خدمة Render مجانية ثانية تقرأ من فرع staging فقط — رابط مختلف لا يمس
    رابط الإنتاج إطلاقاً.
  • مشروع Supabase مجاني ثانٍ = قاعدة تجريبية منفصلة مئة بالمئة.
  • متغير بيئة وحيد (STAGING=1) يقلب الكود نفسه إلى «وضع التجريبية»: بلا
    تلغرام، للمدير فقط، ومعلَّم بشريط TEST VERSION في كل مكان.
  بلا STAGING=1 الكود يتصرف إنتاجاً حرفياً كما كان — تحققنا من ذلك بمقارنة
  الناتج المقدم حرفياً (صفر فرق بعد رقم الإصدار).

ما الذي لا يعمل في التجريبية (مقصود وطبيعي):
  • تلغرام كلياً: لا بوت ولا إشعارات تلغرام ولا نسخ تلغرامي — حتى لا يتصادم
    مع الإنتاج. النسخ الاحتياطي عبر زر النسخ داخل التطبيق (تنزيل ملف) يعمل.
  • دخول Google: يحتاج تسجيل رابط منفصل لكل نطاق لدى Google — استخدم اسم
    الدخول والرقم السري في التجريبية (يمكن تفعيل Google لاحقاً بموافقتك).
  • البريد (استعادة الرقم السري/الرموز): بلا مفاتيح SMTP في التجريبية —
    استخدم «توليد رقم سر مؤقت» من داخل حساب المدير في التجريبية.
  • النوم المجاني: Render يوقف الخدمة بعد ~15 دقيقة خمول — أول فتح يأخذ نحو
    دقيقة (الإنتاج نفسه كذلك). ومشروع Supabase المجاني يتوقف بعد أسبوع خمول —
    زر Restore من لوحة Supabase يعيده.
  التكلفة الإجمالية: صفر.

────────────────────────────────────────────────────────────────────────
الخطوة 1 — قاعدة البيانات التجريبية (Supabase) — 5 دقائق
────────────────────────────────────────────────────────────────────────
  1) ادخل supabase.com بحسابك (نفس حساب الإنتاج).
  2) New project → الاسم: leroi-staging → Database Password: اختر كلمة قوية
     واحفظها عندك → Region: نفس منطقة مشروع الإنتاج (أقرب للمستخدمين) →
     Create new project → انتظر دقيقة حتى يجهز.
  3) من لوحة المشروع: زر Connect (أعلى اليسار) → اختر Connection string →
     URI → انسخ الرابط الذي يبدأ بـ postgresql://...
     (اختر «Session pooler» أو Direct — كلاهما يعمل؛ الرابط ينتهي بـ
     ?sslmode=require — اتركه كما هو).
  4) هذا الرابط هو DATABASE_URL الخاص بالتجريبية — احفظه، ولن يُشار به
     لأي شيء آخر. قاعدة الإنتاج غير مرتبطة به إطلاقاً وبأي شكل.

────────────────────────────────────────────────────────────────────────
الخطوة 2 — فرع staging على GitHub — دقيقتان
────────────────────────────────────────────────────────────────────────
  1) افتح مستودعك على GitHub (المتصل بـ Render).
  2) فوق قائمة الملفات: قائمة الفروع (مكتوب main) → اكتب في خانة البحث:
     staging → «Create branch: staging from main» → تم. main لم يتغير.
  3) الآن ارفع ملف bot.py الجديد (v183) على هذا الفرع فقط:
     تأكد أن الفرع المختار في القائمة هو staging → Add file → Upload files →
     اسحب bot.py → Commit changes.
     ⚠️ لا ترفع شيئاً على main — main للنسخة الرسمية فقط.

────────────────────────────────────────────────────────────────────────
الخطوة 3 — خدمة Render التجريبية — 5 دقائق
────────────────────────────────────────────────────────────────────────
  1) Render Dashboard → New + → Web Service → اختر نفس المستودع.
  2) Language: Docker إذا كان الإنتاج كذلك، أو نفس إعدادات الإنتاج تماماً
     (Build/Start command انسخهما من صفحة خدمة الإنتاج Settings).
  3) Branch: اختر staging (وليس main!) — هذا هو السر كله.
  4) Name: leroi-staging → سيصبح الرابط: https://leroi-staging.onrender.com
  5) Instance Type: Free.
  6) Environment Variables — أضف فقط هذه:
        STAGING        = 1
        DATABASE_URL   = (رابط الخطوة 1 من Supabase التجريبية)
        RENDER_EXTERNAL_URL = https://leroi-staging.onrender.com
     ⚠️ لا تضف أبداً في التجريبية: BOT_TOKEN أو WEBHOOK_URL أو DATABASE_URLS
     أو SMTP_* أو GOOGLE_* أو TEXTBEE_* أو BREVO_API_KEY أو BACKUP_CHANNEL_ID
     أو BACKUP_EMAIL — الباقي غير ضروري، والكود يعمل بلاها.
  7) Health Check Path: /health (نفس الإنتاج إن كان كذلك، أو اتركه فارغاً).
  8) Create Web Service → يبنى ويحاول الإقلاع.
  9) التأكد من اللوج (Logs) — يجب أن ترى:
        [STARTUP] ===== BOT 59 [STAGING — TEST] (invoice-archive ...
        [BOT] STAGING mode — web-only: Telegram polling + daily auto-backup disabled
     إن ظهر الرقم 59 مع [STAGING — TEST] فكل شيء مضبوط.

────────────────────────────────────────────────────────────────────────
الخطوة 4 — أول دخول على التجريبية — دقيقة
────────────────────────────────────────────────────────────────────────
  1) افتح https://leroi-staging.onrender.com (أول فتح بعد النوم = انتظر نحو
     دقيقة).
  2) سترى فوراً الشريط الأحمر أعلى الصفحة:
     «🧪 TEST VERSION — نسخة تجريبية للتجربة فقط — بيانات المحل الحقيقية
     منفصلة تماماً» + شارة TEST في زاوية الشاشة دائمة.
  3) القاعدة فارغة → تظهر شاشة إعداد أول مدير → أنشئ حسابك (اسم دخول + رقم
     سر) → أنت المدير في التجريبية.
  4) المستخدمون الحقيقيون غير موجودين هنا إطلاقاً (قاعدة منفصلة) — ولن
     يستطيع أي موظف الدخول حتى لو حاول: رسالة «لحساب المدير فقط».

────────────────────────────────────────────────────────────────────────
الخطوة 5 — سير العمل اليومي (الموافقة اليدوية قبل كل نشر)
────────────────────────────────────────────────────────────────────────
  1) أجهّز لك أي تحديث جديد وأرسله في حزمة vXXX كالعادة.
  2) ترفع ملفات الحزمة على فرع staging فقط → Render يعيد بناء التجريبية
     تلقائياً خلال دقيقتين.
  3) تختبر بحرية كاملة: دخول، منتجات، مخزون، مستخدمين، فواتير، نسخ احتياطي
     واسترجاع — كل شيء يقع على قاعدة التجريبية فقط.
  4) أُرضيك النتيجة؟ → الموافقة = دمج واحد صريح:
     GitHub → Pull requests → New pull request → base: main ← compare:
     staging → راجع الفرق (ملف واحد غالباً: bot.py) → Merge pull request.
     → الإنتاج ينشر تلقائياً بعد ثوانٍ وتتحدث الواجهة داخلياً بصمت.
  5) لم تعجبك؟ → أغلق الـPR أو تجاهله — main لم يمسّه شيء، ونصلح على
     staging ونعيد الاختبار.

────────────────────────────────────────────────────────────────────────
الخطوة 6 — الرجوع لآخر إصدار مستقر (إن ظهرت مشكلة بعد النشر)
────────────────────────────────────────────────────────────────────────
  • الأسرع (دقيقة واحدة، بلا رفع ملفات): Render → خدمة الإنتاج → تبويب
    Deployments → اختر آخر نشر كان سليماً → Redeploy/Rollback. يرجع فوراً.
  • أو: احتفظ بحزم الإصدارات التي أرسلها لك (v182.zip، v183.zip...) وارفع
    حزمة آخر إصدار مستقر على main من جديد.
  • البيانات: لم تُمس أصلاً — كل التجارب كانت على قاعدة التجريبية، وقاعدة
    الإنتاج بمنأى عن كل ما يحدث في التجريبية.

────────────────────────────────────────────────────────────────────────
خريطة الطلبات العشرة → أين تحققت
────────────────────────────────────────────────────────────────────────
  1) فحص البنية قبل التعديل            → تم (موثق في CHANGELOG v183).
  2) فرع staging مستقل و main للرسمية   → الخطوة 2.
  3) نسخة Render مستقلة على فرع staging → الخطوة 3.
  4) قاعدة تجريبية منفصلة كلياً         → الخطوة 1 (رابط مستقل، صفر مشاركة).
  5) المدير فقط باستخدام النظام الحالي  → بوابة الفئة admin + تعطيل التسجيل.
  6) مؤشر TEST VERSION واضح            → الشريط + الشارة + العنوان + الإصدار.
  7) تجربة كل الوظائف بما فيها النسخ    → كل الـAPI يعمل على قاعدة التجريبية.
  8) لا نشر إلا بموافقتك الصريحة        → الدمج عبر PR = موافقتك بنقرة واحدة.
  9) آلية بسيطة للدمج إلى main          → الخطوة 5 (PR يحفظ سجل القرارات).
 10) الرجوع لآخر إصدار مستقر            → الخطوة 6 (Rollback بنقرة).

ملاحظة أخيرة: هذا الدليل + الحزمة جاهزان، ولا شيء يتغير في إنتاجك قبل أن
تنفذ أنت الخطوات 1-3 بيديك — لا أستطيع ولا أحتاج لمس حسابات GitHub/Render/
Supabase مباشرة، وكل ما أعددته هنا بنقرات لا تحتاج خبرة تقنية.
